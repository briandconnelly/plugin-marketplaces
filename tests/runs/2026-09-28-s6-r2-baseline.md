## Final report

## Audit of the acme-tools marketplace before announcing it to Claude Code and Codex users

I found blocking problems. As the repo stands, 1 of the 7 listed plugins fails to install in Claude Code and 3 fail in Codex. The "guard" safety plugin installs in both but blocks nothing. I didn't change any repo files (`git status` is clean). All my test copies and throwaway config homes are under `$RUN/repo/.tool-homes/`.

**How I checked:**
- Ran `claude plugin validate` (plain and `--strict`) on the marketplace and on each plugin, using Claude Code 2.1.284.
- Added the marketplace and installed its local plugins in a separate isolated setup for each client, using `claude plugin marketplace add` / `claude plugin install` and `codex plugin marketplace add` / `codex plugin add` (codex-cli 0.157.1).
- Edited scratch copies to find the exact cause of each failure, and checked that each fix makes the plugin show up.
- I didn't contact GitHub or send any prompt to a model, so the two remote plugins' contents are unchecked.

File paths below are relative to `$RUN/repo/`. The marketplace file is `.claude-plugin/marketplace.json`.

### Blockers

1. **`fmt` can't be installed in either client.**
   - The entry has `"source": "plugins/fmt"`, without the leading `./`.
   - The Claude validator fails with `plugins.2.source: Invalid input`, and `claude plugin install fmt@acme-tools` fails with the same message.
   - Codex leaves `fmt` out of `codex plugin list` without any error.
   - Changing it to `"./plugins/fmt"` in a copy fixed both clients and made the validator pass.

2. **`guard` doesn't block anything, in either client.**
   - The entry sets `"hooks": "./hooks/hooks.json"`, but `plugins/guard/` has no `hooks/` directory at all. The only thing it ships is a skill that describes blocking commands, and a skill can't enforce anything.
   - In Claude it installs, then shows `Status: ✘ failed to load` with `Hook load failed: hooks: the file-path and array forms are not yet supported in a marketplace entry…`.
   - In Codex it installs as "enabled" with no error, and still has no hook.
   - `claude plugin validate`, even with `--strict`, doesn't catch this.
   - For a plugin sold as a safety guard this is the worst failure: users will think they're protected when they aren't.
   - Fix: ship a real `plugins/guard/hooks/hooks.json` (or put the hooks in the plugin's `plugin.json`), and remove the `hooks` field from the marketplace entry.

3. **`lint` fails to install in Codex because of a name mismatch.**
   - The marketplace entry is named `lint`, but `plugins/lint/.claude-plugin/plugin.json` says `"name": "linter"`, and so does the skill.
   - `codex plugin add lint@acme-tools` fails with: `plugin.json name 'linter' does not match marketplace plugin name 'lint'`.
   - Claude installs it quietly as `lint`, and the validator doesn't flag it.
   - Fix: use one name in both places.

4. **`notes` is invisible to Codex users.**
   - Codex skips entries that use `"source": "github"`, whether or not `sha` or `ref` is present.
   - When I rewrote it as `{"source":"url","url":"https://github.com/acme/notes.git","ref":"v2.0.0","sha":"…"}`, Codex listed it. Claude lists the github form as available.
   - I didn't check that SHA `3add7b9…` really is tag `v2.0.0` in `acme/notes`, because that needs network access.

### Should fix

5. **`deploy` shows the wrong version.** The marketplace entry says `"version": "2.0.0"`, but the plugin's `plugin.json` says `1.9.0`.
   - The validator warns that `plugin.json` wins at install time.
   - I confirmed it: Claude's browse list shows 2.0.0, while both clients install 1.9.0.
   - Fix: remove the entry's version or make the two match.

6. **`remote-x` isn't pinned.** Its source is `ref: "main"` with no `sha`, so whatever lands on `main` reaches users with no review step. I didn't review the plugin's contents (no network access). Pin it to a tag plus a SHA, as `notes` does.

7. **Four plugins are empty stubs.**
   - The `deploy`, `fmt`, `lint` and `guard` skills each contain one sentence that repeats their description.
   - None of them say what "the team's style", "the team's linters" or the staging deploy steps actually are, so the agent will improvise.
   - `ok-tools` is the only plugin with real instructions.

8. **The model can start a deploy on its own.** `plugins/deploy/skills/deploy/SKILL.md` has nothing that stops the model from invoking it automatically. Consider `disable-model-invocation: true`, so a deploy to staging only happens when someone asks for it. (This one is my judgment; I didn't test it.)

### Minor

9. **The README has no install instructions.** `README.md` is three lines ("For Claude Code and Codex users."), with no marketplace-add or install commands for either client and no plugin list.
   - Codex reads `.claude-plugin/marketplace.json` directly; I confirmed this on 0.157.1. That's the path to point Codex users at.
10. **The name `ok-tools` doesn't describe what it does** (formatting Markdown tables and headings).
11. **The skill descriptions are weak triggers.** Each is "Use when you want to <restated description>", with no cue phrases or file types, so the model will struggle to know when to use them.
12. **The owner block has only a name**, with no contact and no license. The strict validator didn't flag this.

### What passed

- Each plugin's own `plugin.json` validates cleanly.
- `ok-tools` and `deploy` install and load in both clients.
- `lint` installs and loads in Claude.

I also confirmed the validator only reports the `fmt` error even though other entries have problems. Re-running on a copy with `fmt` fixed showed the rest of what it finds: only the `deploy` version warning. It didn't flag findings 2, 3, 4 or 6. A clean `claude plugin validate` doesn't show that either client will work, so re-run the Codex install check after fixes.
